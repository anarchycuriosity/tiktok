## 0.2 本轮只建立一条可验证的主路径

| 已经知道 | 本节建立 | 刻意推迟 |
| --- | --- | --- |
| 仓库是 Go 后端 | 注册 → 发布视频 → 获取列表 → 实际播放 | 手机安装、局域网访问、点赞关注聊天、生产部署、主从复制 |

这次运行时，电脑上长期存在三个 Go 进程：API、user、video；另有 MySQL、etcd 和 MinIO。浏览器负责播放，数据库只保存视频信息，真正的 MP4 文件保存在 MinIO。

```text
终端验收脚本 ──注册/发布请求──> API :8089 ──RPC──> user :8085 / video :8086
                                  │                   │
                                  └──向 etcd 查地址     ├──MySQL：账号、视频记录
                                                      └──MinIO：MP4、封面、默认图片
浏览器 <──验收页里的 play_url / cover_url── MinIO :19000
```

这里的箭头分两段：API 返回列表和地址；浏览器拿着地址另外请求 MinIO 的文件。API 能访问，不代表视频地址一定能访问。
例如发布接口刚插入一条记录时，后台还在上传 MP4、截取封面；此时列表可能已有记录，但媒体尚未可读。因此验收脚本会轮询，直到视频和封面都能下载，才报告成功。

本地演示只启动这条路径所需的服务。**页面上的视频来自真实注册、发布和 Feed 接口，不是假数据；这个播放页是本次新增的验收辅助页，不是原项目的完整前端。**

## 0.3 准备环境：所有命令都在 Ubuntu / WSL 终端运行

Windows 用户先打开 Ubuntu 终端，再进入自己的仓库目录。例如本机是：

```bash
cd /home/curiosity/code_practice/go_practice/tiktok-reference
```

在其他电脑上请替换路径。后续命令都以仓库根目录为当前目录，不要在 PowerShell 里逐条执行 Bash 命令。

需要已经安装并运行 Docker Engine 或接入 WSL 的 Docker Desktop，同时具备 Docker Compose v2。先检查：

```bash
docker compose version
docker info
```

如果仅第二条提示访问 `/var/run/docker.sock` 权限不足，可先执行 `sudo docker info` 确认权限；演示脚本检测到此情况后会使用 `sudo docker`，可能要求输入 Ubuntu 密码。不要为解决该问题把 socket 改成所有用户可写。

Ubuntu 上安装其余工具：

```bash
sudo apt-get update
sudo apt-get install -y curl git python3 ffmpeg
```

**不用替换系统 Go。** 演示脚本会在 `.local_demo/tools/` 下载独立的 **Go 1.19.13**。本次使用系统 Go 1.22.2 编译时，旧版 Sonic/Frugal/PID 依赖报错；改用 Go 1.19.13 后通过。不要把「go.mod 写着 1.19」理解成「任意更新的 Go 都能编译」。

首次运行需要联网下载工具链、Go 依赖和容器镜像，并编译 MinIO。下载和编译可能持续数分钟，期间尚无播放页；以终端实际报错和最终提示判断进度。

## 0.4 启动，再执行一次真实发布

依次执行，第一条成功结束后再执行第二条：


- 从固定的 MinIO 官方源码版本 `RELEASE.2023-02-10T18-48-39Z` 构建服务，以及匹配时期的 `mc` 客户端。这里绕开了本次已拉取失败的旧 MinIO 镜像；它们仅用于复现旧项目的本地实验。[MinIO 官方源码](https://github.com/minio/minio/tree/RELEASE.2023-02-10T18-48-39Z)
- 在 `.local_demo/config/` 生成专用配置，不覆盖仓库原来的 `config/`。三个数据库角色都指向同一个演示 MySQL，避免没有配置复制时读不到新数据。
- 创建四个存储桶，补齐 `default0.png`～`default9.png` 和 `default_background.jpg`。只有视频文件还不够，返回作者信息时也会生成这些图片的地址。

## 0.6 停止、重启与定位失败位置

停止本次演示进程和容器，保留数据：

```bash

```

下次仍运行 `start`，随后运行验收命令。退出启动命令所在终端不会自动停止服务；使用上面的 `stop`。
数据库保存在 `tiktok_local_demo_mysql_data` Docker 卷，媒体保存在 `.local_demo/minio_data/`；本指南不要求删除它们。
如果启动中途失败，也可以运行 `stop` 停止已经启动的演示组件，再根据日志处理首个错误。

先查相应日志，不要反复运行旧的 `startup.sh`：

```bash
tail -n 60 .local_demo/api.log
tail -n 60 .local_demo/user.log
tail -n 60 .local_demo/video.log
tail -n 60 .local_demo/minio.log
tail -n 60 .local_demo/viewer.log
```

| 现象 | 含义与处理 |
| --- | --- |
| 下载/构建失败，尚未出现启动成功提示 | 根据首个错误检查 Go 下载、GitHub、Go 代理或镜像仓库的网络。修复网络后重跑；首次没有缓存需要更久 |
| `address already in use` / 容器端口绑定失败 | 检查 8085、8086、8089、12379、13309、18090、19000、19001 是否被其他进程占用；先停止已知的旧实例，不要盲目结束其他项目 |
| `missing go.sum entry` 或导入路径包含 `dousheng/pkg/...` | 使用本 fork 的修正版文件；原始基线存在依赖记录缺失和旧模块路径问题 |
| `Unsupported Go version`、`undefined: _ModuleData` 或汇编错误 | 用脚本固定的 Go 1.19.13，不要直接用系统新版本执行旧启动脚本 |
| `protobuf just support 'framed' trans proto`，随后 API 500 | 原复用传输与该 Kitex 版本的 Protobuf 不匹配；本 fork 已改为 Framed，重新编译启动，不要继续运行旧二进制 |
| `video_list` 为空 | 空数据库不会自带视频。运行验收命令发布；只有存储桶中有 MP4、数据库中没有投稿记录，也不会出现在 Feed |
| 发布返回成功，但视频暂时 404 | 返回只保证记录创建。等待验收脚本确认；持续失败看 `video.log` 中上传、FFmpeg 和封面错误，失败时记录可能被后台删除 |
| `NoSuchBucket` / `NoSuchKey` | 确认四个桶和默认图片已准备好；只创建 `tiktok-videos` 不足以完成发布封面和作者图片读取 |
| 页面无视频或链接 403 | 重新执行验收并刷新，获取未过期签名。不要手改签名 URL 的主机名、端口或参数 |
| 401 / token 过期 | 当前注册和登录 token 有效期约五分钟，重新登录；验收脚本每次自动注册并登录 |
| `/douyin/feed/` 与预期不符 | 当前路由注册的是 **`/douyin/feed`，末尾无斜杠**；注册、登录、发布路由则保留示例里的末尾斜杠 |

本机若从 Windows 浏览器访问 WSL 的 localhost 失败，先在 Ubuntu 内确认对应地址可访问，再检查 WSL 的 localhost 转发。这里没有实测手机跨网连接。

# 二、项目实现

## 2.1 技术选型与相关开发文档

本项目包含三大类接口：基础接口、互动接口、社交接口。采用微服务架构以及 Docker 部署的方式。总共需要 16G 存储空间，1

## 2.2 架构设计

### 2.2.1 架构方案

由于抖音的各接口之间耦合度不高，故采用微服务的架构，分为 HTTP、RPC 和 DAL 三层：

- 其中 HTTP 层使用 Hertz 框架接收客户端发来的 HTTP 请求；
- RPC 层使用 Kitex 框架，并用 ETCD 做服务注册与发现；
- DAL 层为数据访问层，包含 Redis 和 MySQL 两部份。

当客户端发来 HTTP 请求时，HTTP 层会调用 RPC层 的 RPC Client，然后 RPC Client 去 ETCD 中心寻找已经注册的对应的微服务，交给
RPC Server 处理。RPC Server 会去调用 DAL 层的数据库，数据库处理完毕后把结果返回给 RPC Server，RPC Server 将其返回给 RPC
Client，最后 RPC Client 返回给 Hertz 并由 Hertz 返回 HTTP 响应结果。

## 2.3 项目代码介绍

### 2.3.1 技术栈

- Hertz：提供 HTTP 服务；Kitex：提供 RPC 服务；ETCD：服务注册与发现；
- JWT：token 的生成与校验；
- Minio：图片和视频的对象存储；
- Gorm：对 MySQL 进行 ORM 操作，Go-Redis：操作 Redis 对频繁访问的数据进行缓存，使用 Gorm 的 db-resolver 插件进行读写分离操作；
- Redis：对点赞/取消赞和关注/取关操作进行缓存，按照一定策略使键过期，并定时同步数据到数据库；
- RabbitMQ：对 Redis 的异步操作、流量削峰；
- Gocron：定时任务，同步 Redis 与 MySQL 之间的数据；
- Viper：读取配置文件；
- Zap：日志打印；Lumberjack：日志分割；
- Nginx：反向代理与负载均衡。

# 四、项目总结与反思

## 4.1 目前仍存在的问题

- **作品发布：** 在作品异步发布下，不能提示用户视频上传失败。
- **消息记录：** 聊天记录获取使用 Redis 作为缓存，每条记录的过期时间为两秒。若 `用户A` 退出与 `用户B` 聊天界面，并在 Redis
  记录未过期之前重新打开与 `用户B`
  的聊天界面，则不会显示聊天记录。如果处理速度跟不上请求速度，导致请求排队，那么在用户退出聊天界面的两秒后不一定能使 `用户A`
  与 `用户B` 的记录在 Redis 中过期。
- **代码简洁性：** 每次抛出错误时都会在后面紧跟日志记录和错误返回，导致代码不简洁。=> 考虑打包处理
- **多人点赞、关注同步问题：** 多人同时点赞或关注同一个对象，最后的结果未达到预期。
- **数据库同步问题：** 若 Redis 与 MySQL 同步时仍有请求进入，则会丢弃后面请求的数据。

## 4.2 已识别出的优化项

- **消息队列 + 缓存 + 定时同步：** 对可能访问频繁的内容（点赞和关注）做分流和缓存处理，避免该类操作反复访问数据库进行 I/O
  操作而造成的处理缓慢。利用单个消费者从 RabbitMQ
  队列中取出消息，保证其与请求顺序的一致性，将点赞数据分别缓存与两个 `Redis` 键中，记作 `Read` 和 `Write`（键后缀为 `r`
  和 `w`）：`Read` 作为高访问率的缓存，设定为定时过期以减轻内存压力；`Write` 不设置过期，定时将数据同步到数据库中，同步后删除
  Redis 中的数据。此处设定将 **同步前最后一次修改后的数据** 作为同步数据，同步时对 Redis 键进行加锁，同步完成释放锁，若此时还有数据到达，则数据等待锁释放。
- **聊天记录获取 + 缓存：** 由于获取消息记录是轮询方案，不能使其直接访问数据库。本优化方案使用 **Redis 缓存**
  获取到的消息，当第一次进入聊天界面时，缓存按照 `{key: token_toUserID, value: create_time}` 存储，并设置过期时间为两秒，当用户发送消息时，更新
  key 对应的 value 为最新发送消息时间。
- **作品异步发布：** 抖声 APP 发布作品请求的最大等待时长为五秒。若等待超时，则无论视频是否发布成功，都返回为“上传失败”。本方案改进为先在数据库中插入记录，再利用
  **协程** 进行异步视频上传。若视频上传失败，则删除刚刚新增的记录。
- **令牌桶消费互斥：** 多个线程竞争同一个 token 做互斥操作。
